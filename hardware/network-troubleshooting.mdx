title: Troubleshoot an Offline robot
description: Bring a robot back from Offline, from the power button to the network flows your IT team has to open.
---

Most robots that stop reporting to Kapptivate have lost power, or lost the network. One physical reboot tells you which, and often settles it on the spot. Start there. The checks below are for the robot that comes back up and still reads **Offline**.

## Before you go on site

Open the robot's page from [your robot list](/equipment/agents). The bar at the top carries its last contact: **This agent is unreachable. (Last seen 4 months ago)**. Read it on the robot that failed, then on the other robots of the same site.

If its neighbours are still reporting, the fault is in that one robot. If they all went quiet within the same hour, something at the site changed. Your IT team will know what, and you save the drive.

**Reboot agent** won't help you here. The command has to reach the robot over the link that is down, so an **Offline** robot never receives it. Press the button on the machine instead.

## What you need on site

- A screen, a keyboard, a mouse, and a video cable, HDMI or VGA depending on the robot model.
- The robot credentials, which support@kapptivate.com issues if you don't have them.
- The IP requirements document, which lists the flows the robot needs to work. Ask support@kapptivate.com for it.
- The local IP address, on your LAN, that those flows were opened for. Your IT team holds it.

## Where to start

Start from what the platform just told you.

| What you see | What you check | Where to go |
|---|---|---|
| One robot on the site is **Offline** | the robot, its power supply, its network cable | [Reboot the robot](#reboot-the-robot) |
| Every robot on the site dropped at the same hour | the site: power, network, firewall | [Check the flows](#check-the-flows), once your IT team has looked |
| On site, the screen stays black or the LEDs freeze | hardware | [A robot that no longer boots](#a-robot-that-no-longer-boots) |

## Reboot the robot

Press the front button to power the robot down. Count ten seconds before you press it again. The platform needs about three minutes to notice the robot came back, so read the status after that, not before. It should read **Online**.

Still **Offline**? Reboot it a second time.

Don't go for a third. Past two, the trouble is no longer software. Move on to power and cables.

## Check power and cables

The sockets you need are on the back panel. Plug in the screen, the keyboard, and the mouse there, then take the connections one at a time.

- Look at the front panel. A dark panel on a robot that is switched on means no power reaches it. Work back through the socket, the power brick, and the cord.
- On a cellular robot, the front LEDs blink around the clock. Frozen or dark LEDs on a lit panel send you to [a robot that no longer boots](#a-robot-that-no-longer-boots). Web and smartphone robots don't carry that signal.
- Check that the RJ45 cable sits in Ethernet port 1, 2, or 3, never port 4, which does not work. [Configure the robot network](/hardware/configure-network#set-the-static-ip) shows the numbering.

Power the robot back up once you have changed something, then read its status again. Front panel lit, platform still **Offline**? The robot runs and nobody hears it, so go to [check the robot's local IP address](#check-the-robot-s-local-ip-address).

## A robot that no longer boots

The front panel is lit, the screen stays black: the robot no longer boots. Frozen LEDs on a cellular robot say the same thing. Rule out the false alarm first, by checking the screen's input source against the socket you actually used.

Source right, nothing changed after two reboots? Stop here. No command runs on a robot that won't boot, so nothing below this line applies. Send the case to support@kapptivate.com, naming the robot as the platform names it. On a cellular robot, film the front panel and attach the video. The LED sequence shows how far the boot got.

## Check the robot's local IP address

Log in with the robot credentials, then open a terminal from the Linux desktop. One command gives both the robot's local address and its gateway. Nothing leaves the robot: it only reads its own routing table.

```bash
ip route get 1.1.1.1
```

```
1.1.1.1 via 192.168.10.1 dev eno1 src 192.168.10.42 uid 1000
    cache
```

Two values matter on that line. `src` is the robot's own address, `192.168.10.42` above. `via` is the gateway it goes through to leave the network, `192.168.10.1`. The `src` value has to match the address your IT team wrote into the firewall rules. When it doesn't, give the robot [its static IP](/hardware/configure-network#set-the-static-ip) again, and the rules find it where they expect it.

The other possible answer is shorter, and it ends the question here.

```
RTNETLINK answers: Network is unreachable
```

No route means no link at all. Go back to the RJ45 cable and the switch port before anyone mentions firewalls.

Ping that gateway next. Use the address printed after `via`.

```bash
ping -c 4 192.168.10.1
```

```
64 bytes from 192.168.10.1: icmp_seq=1 ttl=254 time=1.12 ms
64 bytes from 192.168.10.1: icmp_seq=2 ttl=254 time=1.18 ms
64 bytes from 192.168.10.1: icmp_seq=3 ttl=254 time=1.09 ms
64 bytes from 192.168.10.1: icmp_seq=4 ttl=254 time=1.15 ms

--- 192.168.10.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3004ms
```

Replies mean the robot sits on its network. Move on to the flows. The other outcome looks like this.

```
--- 192.168.10.1 ping statistics ---
4 packets transmitted, 0 received, 100% packet loss, time 3007ms
```

Go back to the RJ45 cable, which can be faulty or in the wrong socket. Then have your IT team confirm it lands on a live switch port.

## Check the flows

Does your robot go straight out to the internet? Then there is nothing to open, and the page ends for you at the gateway. What follows is for a filtered corporate network.

There, the IP requirements document lists the destinations the robot has to reach, with their port. They are independent: control, results, and support access each take their own. So a robot can happily receive its tests and send back nothing at all. Test every line, not the one you suspect.

Every connection here is outbound. You never have to let anything in from the internet.

<Tip>
  The rules were opened for one address, the robot's. Run these commands anywhere else on the same network and they can all pass while the robot still fails.
</Tip>

Work down the document, one line at a time, replacing `ADDRESS` and `PORT` with the values it gives.

```bash
nc -zv -w 5 ADDRESS PORT
```

Three answers come back.

```
Connection to 203.0.113.10 443 port [tcp/https] succeeded!
```

The flow is open. Move to the next line.

```
nc: connect to 203.0.113.10 port 443 (tcp) failed: Connection refused
```

Something on the other end answered, then shut the door. A rule rejects the traffic outright, or the service behind that port is gone. Either way, the line goes to your IT team.

```
nc: connect to 203.0.113.10 port 443 (tcp) timed out: Operation now in progress
```

Nothing answered, and `-w 5` gives up after five seconds. Silence means the packet was dropped, not refused. Behind a corporate firewall, that is a rule nobody ever wrote.

### Run the test again by domain name

Work down the list a second time, swapping each IP address for its domain name.

```bash
nc -zv -w 5 robots.example.com 443
```

```
nc: getaddrinfo for host "robots.example.com" port 443: Name or service not known
```

An address that passes while its name fails clears the firewall. DNS is at fault, and the fix is one field. Fill **DNS servers** in the Enter the addresses step of [set the static IP](/hardware/configure-network#set-the-static-ip).

### Rule out a proxy decrypting the traffic

One failure still reads like a success. `nc` gets through, and the robot still reaches nobody, because something in between is decrypting the traffic. Ask an HTTPS destination for its status code.

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://robots.example.com
```

```
200
```

The connection runs end to end. Nothing to do on that destination.

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

An intermediate device is presenting its own certificate, and the robot refuses to trust it. The `issuer` line names that device. `-k` is there to read the certificate, not to trust it: without the flag, `curl` stops before printing it.

```bash
curl -kv https://robots.example.com 2>&1 | grep issuer
```

A public authority signs a healthy connection:

```
*  issuer: C=US; O=Let's Encrypt; CN=YR1
```

Your own company's name on that line points at the proxy:

```
*  issuer: C=FR; O=Your Company; CN=Your Company Root CA
```

Ask your IT team to exempt the destinations in the document from TLS inspection.

## Who to contact

Whatever failed above belongs to your own network: a line of the document, a silent gateway, a certificate from the wrong authority. Send your IT team the full command output. Add the robot's local IP address and the time you ran the test. Once the rule is open, run the command again from the robot, and the status follows within minutes.

Every check passes and the platform still says **Offline**? That one is ours. Write to support@kapptivate.com with the robot's name as the platform shows it. Its local IP address helps too, if you noted it.

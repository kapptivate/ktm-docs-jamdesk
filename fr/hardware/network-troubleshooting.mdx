---
title: Dépanner un robot Offline
description: Faire remonter un robot passé Offline, du redémarrage physique jusqu'aux flux réseau que votre service informatique doit ouvrir.
---

La plupart du temps, un robot qui ne remonte plus dans Kapptivate n'a plus d'alimentation électrique, ou n'est plus connecté au réseau. Le premier réflexe reste de le redémarrer physiquement. S'il reste **Offline** après ce redémarrage, vérifiez sa configuration réseau. Cette page déroule les deux dans l'ordre.

## Avant de vous déplacer

Ouvrez la fiche du robot depuis [la liste de vos robots](/fr/equipment/agents). Le bandeau du haut affiche sa dernière connexion : **Cet agent est inaccessible. (Dernière connexion il y a 4 mois)**. Relevez cette date sur le robot en panne, puis sur les autres robots du même site.

Si le problème ne concerne qu'un seul robot, l'investigation est à effectuer au niveau du robot. Si le problème concerne plusieurs robots, tombés au même moment, l'investigation est à effectuer au niveau du site qui héberge les robots. Dans ce cas, prévenez votre service informatique.

<Frame caption="La fiche d'un robot Offline sur la plateforme">
  ![La fiche du robot demo-web-1, au statut Offline, avec son bandeau de dernière connexion et le bouton de redémarrage](/images/hardware/network-troubleshooting-01.webp)
</Frame>

Le bouton **Redémarrer l'agent** ne sert à rien sur un robot **Offline** : la commande emprunte le lien qui est justement coupé. Seul un redémarrage physique le fait remonter.

## Ce qu'il vous faut sur place

- Un écran, un clavier, une souris et un câble vidéo, HDMI ou VGA selon le modèle de robot.
- Les identifiants du robot. Demandez-les à support@kapptivate.com si vous ne les avez pas.
- Le document des exigences IP, qui liste les flux nécessaires au fonctionnement du robot. Demandez-le à support@kapptivate.com.
- L'adresse IP locale, sur votre LAN, pour laquelle ces flux ont été ouverts. C'est votre service informatique qui la détient.

## Par où commencer

Partez de ce que vous venez de lire sur la plateforme.

| Ce que vous constatez | Ce que vous vérifiez | Où aller |
|---|---|---|
| Un seul robot du site est **Offline** | le robot, son alimentation, son câble réseau | [Redémarrer le robot](#redémarrer-le-robot) |
| Tous les robots du site sont tombés à la même heure | le site : courant, réseau, pare-feu | [Vérifier les flux](#vérifier-les-flux), après le passage de votre service informatique |
| Sur place, l'écran reste noir ou les voyants se figent | le matériel | [Un robot qui ne démarre plus](#un-robot-qui-ne-démarre-plus) |

## Redémarrer le robot

Éteignez le robot avec le bouton en façade, attendez dix secondes, rallumez-le. Laissez-lui environ trois minutes, puis relisez son statut sur la plateforme. Il doit repasser **Online**.

S'il reste **Offline**, redémarrez-le une seconde fois.

Ne redémarrez pas une troisième fois : au-delà, le problème n'est plus logiciel. Passez à l'alimentation et aux câbles.

## Vérifier l'alimentation et les câbles

Branchez l'écran, le clavier et la souris à l'arrière du robot, puis reprenez les branchements un par un.

- Regardez la façade. Si elle reste éteinte, le courant n'arrive pas : vérifiez la prise, le bloc d'alimentation et le cordon.
- Sur un robot cellulaire, les voyants de façade clignotent en permanence. Des voyants figés ou éteints sur une façade allumée renvoient à [un robot qui ne démarre plus](#un-robot-qui-ne-démarre-plus).
- Vérifiez que le câble RJ45 est branché sur le port Ethernet 1, 2 ou 3. Le port 4 ne fonctionne pas, et la numérotation est illustrée dans [configurer le réseau du robot](/fr/hardware/configure-network#définir-une-ip-statique).

Si vous avez modifié un branchement, rallumez le robot et relisez son statut. Si vous avez tout vérifié, et que tout semble correctement branché et allumé, passez à [vérifier l'adresse IP locale du robot](#vérifier-ladresse-ip-locale-du-robot).

## Un robot qui ne démarre plus

La façade est allumée, l'écran reste noir : le robot ne démarre plus. Sur un robot cellulaire, vous constatez aussi que les voyants ne clignotent plus. Vérifiez d'abord la source d'entrée de l'écran, qui doit correspondre au câble branché.

Si la source est la bonne et que rien ne change après deux redémarrages, arrêtez-vous là. Aucune commande ne s'exécute, et le reste de cette page ne vous sert à rien. Remontez le cas à support@kapptivate.com, en nommant le robot tel qu'il apparaît sur la plateforme. Sur un robot cellulaire, filmez la façade et joignez la vidéo.

## Vérifier l'adresse IP locale du robot

Connectez-vous avec les identifiants du robot, puis ouvrez un terminal depuis le bureau Linux. Une seule commande donne l'adresse IP locale et la passerelle.

```bash
ip route get 1.1.1.1
```

```
1.1.1.1 via 192.168.10.1 dev eno1 src 192.168.10.42 uid 1000
    cache
```

`src` donne l'adresse IP locale du robot, ici `192.168.10.42`, et `via` donne la passerelle de son réseau, ici `192.168.10.1`. Comparez l'adresse `src` à celle que votre service informatique a déclarée dans ses règles de pare-feu : les deux doivent coïncider. Si elles sont différentes, vous pouvez reconfigurer [l'IP statique du robot](/fr/hardware/configure-network#définir-une-ip-statique) pour qu'elle corresponde à ce qui est configuré sur votre réseau.

L'autre réponse possible est plus courte, et elle clôt la question du réseau.

```
RTNETLINK answers: Network is unreachable
```

Le robot n'a aucune route, donc aucun lien. Vérifiez le câble RJ45 et le port du switch.

Joignez ensuite la passerelle, en reprenant l'adresse affichée après `via`.

```bash
ping -c 4 192.168.10.1
```

```
64 bytes from 192.168.10.1: icmp_seq=1 ttl=254 time=1.12 ms
64 bytes from 192.168.10.1: icmp_seq=2 ttl=254 time=1.18 ms
64 bytes from 192.168.10.1: icmp_seq=3 ttl=254 time=1.09 ms
64 bytes from 192.168.10.1: icmp_seq=4 ttl=254 time=1.15 ms

--- 192.168.10.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3004ms
```

La passerelle répond : le robot est bien sur son réseau, [passez aux flux](#vérifier-les-flux). L'autre réponse est celle-ci.

```
--- 192.168.10.1 ping statistics ---
4 packets transmitted, 0 received, 100% packet loss, time 3007ms
```

Vérifiez alors le câble RJ45 : il est peut-être défaillant, ou branché au mauvais endroit. Faites ensuite vérifier par votre service informatique qu'il aboutit sur un port de switch actif.

## Vérifier les flux

Si votre robot sort directement sur internet, vous n'avez aucun flux à ouvrir : la page s'arrête pour vous à la passerelle. Ce qui suit ne vaut que sur un réseau d'entreprise filtré.

Le document des exigences IP liste alors les destinations que le robot doit joindre, avec leur port. Elles sont indépendantes : le pilotage, la remontée des résultats et l'accès du support passent chacun par la sienne. Un robot peut donc recevoir ses tests sans en remonter un seul résultat. Testez toutes les lignes, pas seulement celle qui vous paraît en cause.

Toutes ces connexions partent du robot. Aucun flux entrant depuis internet n'est nécessaire.

<Tip>
  Les règles sont ouvertes pour l'adresse IP du robot. Le même test depuis une autre machine peut réussir alors que le robot échoue : lancez ces commandes sur le robot lui-même.
</Tip>

Prenez le document ligne par ligne, en remplaçant `ADDRESS` et `PORT` par les valeurs qu'il donne.

```bash
nc -zv -w 5 ADDRESS PORT
```

Trois réponses sont possibles.

```
Connection to 203.0.113.10 443 port [tcp/https] succeeded!
```

Le flux est ouvert. Passez à la ligne suivante.

```
nc: connect to 203.0.113.10 port 443 (tcp) failed: Connection refused
```

Une machine a répondu et a refusé la connexion. Soit une règle de pare-feu rejette explicitement ce trafic, soit plus rien n'écoute sur ce port. Notez la ligne pour votre service informatique.

```
nc: connect to 203.0.113.10 port 443 (tcp) timed out: Operation now in progress
```

Rien n'a répondu, et `-w 5` abandonne au bout de cinq secondes. Quand rien ne répond, c'est en général qu'aucune règle n'autorise ce flux. Derrière un pare-feu d'entreprise, c'est le cas le plus fréquent.

### Rejouer le test par le nom de domaine

Reprenez ensuite chaque ligne avec le nom de domaine à la place de l'adresse IP.

```bash
nc -zv -w 5 robots.example.com 443
```

Le nom se résout et le flux passe :

```
Connection to robots.example.com (203.0.113.10) 443 port [tcp/https] succeeded!
```

L'autre réponse est celle-ci :

```
nc: getaddrinfo for host "robots.example.com" port 443: Name or service not known
```

L'adresse IP passe mais son nom échoue. Le robot n'a certainement pas de serveur DNS configuré, ce qui l'empêche de résoudre le nom de domaine. Remontez l'information à votre service informatique. Vous pouvez configurer un ou plusieurs serveurs DNS sur le robot en suivant [configurer le réseau du robot](/fr/hardware/configure-network#définir-une-ip-statique).

### Vérifier le certificat

Dernière vérification. Reprenez les destinations du document qui sont en HTTPS, donc celles sur le port 443, et demandez le code de retour.

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://robots.example.com
```

Vous devez obtenir `200` :

```
200
```

Toute autre réponse, et celle-ci en particulier, signale qu'un équipement de votre réseau s'intercale et présente son propre certificat.

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

Remontez alors à votre service informatique que le trafic HTTPS vers les destinations du document est intercepté.

## Qui contacter

Une des étapes de vérification de cette procédure a échoué : le blocage est sur votre réseau. Transmettez la sortie complète des commandes concernées à votre service informatique, avec l'adresse IP locale du robot et l'heure du test.

Toutes les étapes de vérification de cette procédure ont fonctionné et le robot reste **Offline** ? Écrivez à support@kapptivate.com. Donnez le nom du robot tel qu'il apparaît sur la plateforme, et son adresse IP locale si vous l'avez relevée : cela facilitera les investigations.
